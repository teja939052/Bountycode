# 04 PLAN ORCHESTRATOR POLICIES

**BountyCode — Phase 2 Design Freeze**
**Status: Design-only document**
**No application code written**

---

## 1. Purpose

Define the Learning Plan Orchestrator — the single next-action decision owner
for BountyCode. This document separates placement readiness from next-action
selection, establishes the three planning horizons, and defines the deterministic
decision policy.

This is a design document. No implementation is authorized.

---

## 2. Ownership Separation

### 2.1 Readiness Engine ≠ Orchestrator

| Question | Owner | Example |
|----------|-------|---------|
| "Is this learner ready for TCS assessment?" | Readiness Engine | Overall score 78/100, coverage 0.85 → "ready" |
| "What should this learner do next?" | Learning Plan Orchestrator | "Repair loop boundary misconception in dsa.arrays" |

Readiness Engine outputs a score and coverage. It does NOT choose the next
learning activity. The Orchestrator consumes readiness output as one input
among many.

### 2.2 Component Responsibility Matrix

| Responsibility | Owner | Input | Output |
|----------------|-------|-------|--------|
| Profile/context | Onboarding service | Student goals, company, role | Learner context |
| Learner state | BKT / Learner State Engine | Evidence events | State estimate per skill |
| Content catalogue | Question Store / Content Loader | Versioned files | Servable content |
| Skill graph | Prerequisite Graph | Skill definitions | DAG, prerequisite plans |
| Diagnostic | Assessment service | Evidence gaps | Diagnostic results |
| Repair | Repair Service | Misconception flags | Repair missions |
| SRS | Spaced Repetition | ReviewCard state | Due reviews |
| Mastery | Mastery Engine | Question evidence | 0-5 mastery levels |
| Readiness | Readiness Engine | Skill scores | Placement score |
| Adaptive ranker | Adaptive Action Planner | Candidate actions | Ranked list |
| **Next-action decision** | **Learning Plan Orchestrator** | **All above** | **One next action** |

## 3. Three Planning Horizons

All three are views of ONE coherent plan generated by the Orchestrator.

### 3.1 Learning Journey (Long-Term)

| Field | Description |
|-------|-------------|
| `target_company` | e.g., `"tcs"` |
| `target_blueprint_id` | Assessment blueprint |
| `target_skills` | Array of canonical skill IDs |
| `current_skill` | Skill currently being worked on |
| `progress` | Percentage of blueprint skills at readiness threshold |
| `estimated_weeks` | Estimated weeks to readiness |

### 3.2 Today's Plan (Time-Bounded)

| Field | Description |
|-------|-------------|
| `date` | ISO date |
| `time_budget_minutes` | Student's available time today |
| `activities` | Array of scheduled activities |
| `total_estimated_minutes` | Sum of activity durations |
| `remaining_minutes` | Time budget minus activities |

### 3.3 Next Learning Step (Immediate)

| Field | Description |
|-------|-------------|
| `kind` | `"repair"` / `"review"` / `"diagnostic"` / `"learn"` / `"practice"` / `"assess"` / `"mock"` |
| `skill_id` | Canonical skill ID |
| `lesson_id` | Lesson identifier (if applicable) |
| `reason` | Human-readable explanation |
| `estimated_minutes` | Time estimate |
| `content_version` | Content version |
| `decision_trace` | Array of reasoning steps |

## 4. Decision Policy

### 4.1 Priority Rules (Ordered)

The Orchestrator evaluates candidate actions in this order:

| Priority | Condition | Action Kind | Rationale |
|----------|-----------|-------------|-----------|
| 1 | Active misconception with repair mission available | `"repair"` | Fix confirmed misconceptions first |
| 2 | Due SRS review available | `"review"` | Prevent decay of known skills |
| 3 | Prerequisite blocker unassessed or needs review | `"diagnostic"` | Can't build on weak foundations |
| 4 | In-progress activity below mastery threshold | `"practice"` | Complete what was started |
| 5 | Next unassessed skill in prerequisite order | `"learn"` | Build foundations in order |
| 6 | Transfer opportunity for independent skill | `"transfer"` | Prove capability in changed context |
| 7 | Company blueprint gap | `"mock"` | Prepare for target company |
| 8 | Stretch work (above readiness) | `"practice"` | Extension for advanced learners |

This is NOT a rigid priority order. Conflicts are resolved by explicit rules
in Section 4.3.

### 4.2 Candidate Selection Constraints

A candidate action is eligible only when ALL of the following are true:

| Constraint | Check |
|------------|-------|
| Content trust | Content is `verified` or `reviewed` (not UNVERIFIED) |
| Prerequisites | All prerequisite skills at Competent (level 3+) or action is diagnostic/repair |
| Time budget | `estimated_minutes <= remaining_minutes` |
| Content quality | `content_quality >= 0.55` (per Adaptive Action Planner) |
| No unnecessary repetition | Same lesson not completed recently without new evidence |
| Difficulty fit | Matches learner's estimated capability ±1 level |
| Multiple goals | Respects student's company and role targets |

### 4.3 Conflict Resolution

| Conflict | Resolution Rule |
|----------|-----------------|
| Repair vs. Due Review | Repair wins (misconception blocks new learning) |
| Review vs. New Learning | Review wins if decay risk high (>7 days since last practice) |
| Prerequisite vs. New Skill | Prerequisite wins (no building on weak foundations) |
| Time budget too small | Return `"no_feasible_action"` with reason, not a truncated activity |
| Multiple companies/roles | Use primary target_company; secondary only if time permits |
| Evidence conflict (BKT says independent, Mastery says level 2) | Use more conservative estimate for teaching decisions |

### 4.4 Decision Trace

Every Orchestrator decision produces a human-readable trace:

```json
{
  "decision_trace": [
    "Active misconception ZERO_BASED_INDEX_CONFUSION found for dsa.arrays",
    "Repair mission available: teach_and_reassess",
    "No due SRS reviews",
    "Prerequisite coding.loops met at level 3",
    "Selected repair action: teach_and_reassess"
  ],
  "confidence": "high",
  "rejected_alternatives": [
    {"kind": "learn", "skill_id": "dsa.two_pointers", "reason": "prerequisite dsa.arrays not mastered"},
    {"kind": "review", "skill_id": "coding.variables", "reason": "no due reviews"}
  ]
}
```

## 5. Adaptive Action Planner Integration

The existing `adaptive_action_planner.py` provides `rank_actions()` with
versioned `PlannerWeights`. The Orchestrator uses it as follows:

1. Generate candidate actions from all engine outputs
2. Filter candidates by constraints (Section 4.2)
3. Pass remaining candidates to `rank_actions()` with `PlannerWeights`
4. Select top-ranked action as the next step
5. Record decision trace with rationale

### 5.1 PlannerWeights (Existing)

| Field | Default | Meaning |
|-------|---------|---------|
| `retention` | 0.15 | Weight for retention urgency |
| `uncertainty` | 0.10 | Weight for uncertainty reduction |
| `minimum_content_quality` | 0.55 | Minimum content quality threshold |
| `version` | `"blpa-v1-heuristic"` | Policy version |

The Orchestrator may tune weights only through measured evaluation, not
arbitrary changes.

## 6. Determinism Requirements

### 6.1 Deterministic Behavior

| Input Condition | Required Output |
|-----------------|-----------------|
| Same normalized input + same policy version | Same next action |
| Null/missing evidence | `"insufficient_evidence"` action, not random guess |
| Duplicate events | Deduplicated; no double-counting |
| Invalid inputs | Clear error, not silent fallback |
| Boundary values | Handled explicitly |
| Unsupported states | `"no_feasible_action"` with reason |
| Content version changes | Re-evaluate all candidates |
| Policy version changes | Re-evaluate all candidates |
| Conflicting evidence | More conservative estimate for teaching |

### 6.2 No Random Selection

No arbitrary random selection in authoritative learning decisions. If variety
is required (e.g., selecting among equally-ranked candidates), use deterministic
seeded selection and persist the seed and selection context.

### 6.3 No LLM Decisions

The Orchestrator does NOT use an LLM for:
- Grading answers
- Determining mastery
- Content trust decisions
- Readiness scoring
- Next-action selection

AI may paraphrase approved educational content but must be optional.

## 7. Side-Effect Boundaries

### 7.1 What the Orchestrator May Do

- Read from all engine outputs
- Read from learner state, mastery, readiness, SRS, repair, prerequisite graph
- Write ONE decision record to `gamification_events` (inputs, outputs, reward_policy_version)
- Write ONE decision record to learner context (current next action)
- Return the next action to the frontend

### 7.2 What the Orchestrator May NOT Do

- Write XP, coins, stars, streak, combo, or badges (only `record_practice()`)
- Write mastery levels (only Mastery Engine)
- Write readiness scores (only Readiness Engine)
- Write lesson completion (only Lesson Service after student action)
- Modify content trust status (only human review)
- Modify question bank content (only versioned files)

## 8. Versioning

| Entity | Version Field | Change Trigger |
|--------|--------------|----------------|
| Orchestrator policy | `orchestrator_version` | Change to priority rules or constraints |
| Planner weights | `policy_version` | Change to weights or thresholds |
| Content | `content_version` | Change to lesson/question content |
| Grading | `grading_version` | Change to grading logic |
| BKT parameters | `parameter_version` | Change to p_l0, p_t, p_g, p_s |

All decision records include version fields for audit and replay.

---

## 9. Failure Behavior

| Failure | Behavior |
|---------|----------|
| No eligible candidates | Return `{"status": "no_feasible_action", "reason": "..."}` |
| Engine unavailable | Degrade gracefully; use available engines only; log degradation |
| Content missing | Return `"content_not_available"` with suggested alternative |
| Evidence insufficient | Return `"insufficient_evidence"` with required evidence |
| Prerequisite cycle detected | Return `"invalid_graph"` with cycle details |
| Time budget exhausted | Return `"time_budget_exhausted"` with remaining time |

## 10. Test Strategy

| Test Type | Description |
|-----------|-------------|
| Unit tests | Each priority rule tested in isolation |
| Property tests | Same input → same output across 1000+ seeds |
| Replay tests | Record decision trace; replay produces identical result |
| Boundary tests | Time budget = 0, time budget = 1 minute, no skills assessed |
| Conflict tests | Repair vs. Review, Review vs. New Learning |
| Constraint tests | Untrusted content excluded, prerequisites enforced |
| Integration tests | Full flow from evidence event to next action |
