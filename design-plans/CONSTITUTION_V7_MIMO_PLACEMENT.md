## 0. NON-NEGOTIABLE PRODUCT RULE

BountyCode is ONE product. It must have:

- one learner state
- one curriculum graph
- one progression system
- one lesson experience
- one evidence path
- one mastery system
- one SRS system
- one repair system
- one opportunity graph
- one readiness system
- one gamification law

No agent may create another system that performs the same responsibility.

Before creating a route, API, service, collection, lesson engine, mastery model,
progression model, planner, company engine or learner-state model:

```
SEARCH EXISTING ARCHITECTURE
        ↓
FIND CANONICAL OWNER
        ↓
REUSE / EXTEND
```

If an agent believes a second system is necessary: STOP → DOCUMENT THE CONFLICT →
EXPLAIN WHY THE EXISTING SYSTEM CANNOT SUPPORT IT → DO NOT IMPLEMENT THE DUPLICATE.

## 1. PRODUCT THESIS

BountyCode is not: another coding course, question bank, LeetCode clone, mock-test
platform, AI chatbot, or company-prep website.

BountyCode is: **a personalized learning-to-placement operating system for students
targeting Indian software placements.** The learner should feel that BountyCode knows:
WHO I AM · WHAT I KNOW · WHAT I DON'T KNOW · WHAT I AM TRYING TO ACHIEVE ·
WHICH OPPORTUNITIES I CARE ABOUT · WHAT THOSE OPPORTUNITIES REQUIRE ·
WHAT I SHOULD DO TODAY · WHY I SHOULD DO IT · WHETHER I AM ACTUALLY IMPROVING ·
WHAT I NEED TO REPAIR · HOW READY I AM · WHAT TO DO NEXT.

## 2. THE CORE PRODUCT LOOP

GOAL → DIAGNOSE → PERSONALIZE → TODAY'S MISSION → MICRO-LEARN → INTERACT →
PRACTICE → APPLY → EVIDENCE → MASTERY → REPAIR → RECALL → TRANSFER → PROVE →
READINESS → OPPORTUNITY FIT → NEXT MISSION. The loop must continuously adapt.

## 3. FIVE ENVIRONMENTS

**WORLD** (Where am I going?) — capability map, progression, worlds, milestones,
unlocked skills, long-term journey, placement path.
**LAB** (Help me understand and use things) — the canonical learning experience:
MissionShell → MissionExperience → interactive learning → code/reasoning/visual
manipulation → evidence.
**ARENA** (Can I perform under pressure?) — timed challenges, company-style
assessments, coding/aptitude/reasoning rounds, mocks, boss battles, contests.
**COMMAND** (Am I on track for my target?) — Today, readiness, weakness map,
repair, deadlines, target companies, placement season, progress, next actions.
**CAREER** (Can I convert readiness into an opportunity?) — resume, interview,
projects, company preparation, application tracking, alumni experiences, proof.
No sixth learning environment should be introduced.

## 4. MIMO-INSPIRED EXPERIENCE PRINCIPLES

Adopt Mimo's strongest mechanics: short, interactive, real code, immediate feedback,
daily practice, visible progress, personalized paths, real projects, AI guidance,
mobile-first — taken further by connecting them to placement readiness.

## 5. THE BOUNTYCODE MICRO-LESSON

Meaningful progress in ~1 / 3 / 5 / 10 / 15+ minutes. Do NOT force one duration.
Ask: **How much time do you have?** (⚡1 min · 🔥5 min · 🎯10 min · 🚀20 min ·
🏆 Deep session). The engine chooses an appropriate slice.

## 6. ONE MICRO-LESSON LOOP

Base: INTRO → TINY EXPLANATION → REAL EXAMPLE → DO SOMETHING → IMMEDIATE FEEDBACK → NEXT.
Extended grammar (primitives, engine picks minimum useful subset):
SEE → UNDERSTAND → TOUCH → PREDICT → CHANGE → BUILD → BREAK → FIX → REMEMBER → TRANSFER → PROVE.
Simple concept: SEE → PREDICT → SOLVE → RECALL → PROVE.
Complex: SEE → TOUCH → PREDICT → CHANGE → BUILD → BREAK → FIX → REMEMBER → TRANSFER → PROVE.

## 7. REAL CODE FROM THE BEGINNING

REAL CODE > PSEUDOCODE > PASSIVE THEORY. Touch real code ASAP (Python, Java, C++,
JavaScript, SQL). Simplify the task, never hide real development. Core differentiator:
**ANSWER → CHANGE → OBSERVE → UNDERSTAND** (e.g. predict output, change one value, predict again).

## 8. INSTANT FEEDBACK

Every meaningful action produces useful feedback. Never bare "Incorrect" — prefer
"Not yet" + what to watch. Categories: CORRECT, PARTIALLY CORRECT, MISCONCEPTION,
SYNTAX/LOGIC/EDGE-CASE/STRATEGY ERROR, TIMING ISSUE, RECALL/TRANSFER FAILURE.
Feedback itself becomes evidence.

## 9. THE PERSONALIZATION ENGINE

Learner state = GOAL + CURRENT KNOWLEDGE + MISCONCEPTIONS + CAPABILITIES +
RECENT PERFORMANCE + RECALL STATE + TIME AVAILABLE + DEADLINE + TARGET ROLE +
TARGET COMPANY + ASSESSMENT VERSION + PLACEMENT SEASON.
LEARNER GRAPH + OPPORTUNITY GRAPH + CONTEXT → ADAPTIVE PLANNER → TODAY'S BEST ACTION.

## 10. PERSONALIZATION MUST BE REAL

Every recommendation carries its reason ("Why this mission? …loop tracing remains
weak… target assessments test it… you have 8 minutes…"). Same platform, different
curriculum per learner.

## 11. SERVICE-BASED COMPANY PERSONALIZATION

No isolated per-company courses. Instead: SHARED CAPABILITY GRAPH → COMPANY/ROLE
WEIGHTS → ASSESSMENT VERSION → LEARNER GAP → PRIORITIZATION. Capabilities:
programming fundamentals, DSA, SQL, aptitude, reasoning, verbal, CS fundamentals,
communication, interview, projects. Opportunity profiles weight them.

## 12. OPPORTUNITY GRAPH

Versioned data per opportunity: COMPANY → ROLE → ASSESSMENT VARIANT → VERSION →
EFFECTIVE DATE → SECTIONS → REQUIRED CAPABILITIES → WEIGHTS → TIMING → INTERVIEW
STAGES. Never hardcode assessment patterns in frontend. Support 2025/2026/2027
versions without rebuilding curriculum.

## 13. TARGET SELECTION (onboarding)

Preparing for? (Campus · Service-based · SDE · Specific company · Product · Unsure) →
role → daily time (5/15/30/60/120+ min) → placement start date. Use answers immediately.

## 14. FIVE-MINUTE DIAGNOSTIC

Test, don't ask. Sample programming (trace/predict/modify/debug/implement/transfer),
aptitude (interpret/strategy/calculate/estimate/time), reasoning (represent/deduce/
eliminate/transfer), plus problem solving, SQL, CS fundamentals, communication.
Self-assessment is context, not ground truth.

## 15. THE PERSONALIZED STARTING MAP

Show capability bars, biggest gap + WHY, and TODAY'S BOUNTY (one mission + time + START).
Learner never wonders "what should I study today?"

## 16. THE DAILY HABIT LOOP

OPEN → SEE TODAY → ONE CLEAR MISSION → START INSTANTLY → COMPLETE → FEEDBACK →
REWARD → VISIBLE PROGRESS → NEXT OPTIONAL ACTION. Primary CTA: Continue Today's Bounty.

## 17. PERSONALIZED DAILY PLAN

Today's Bounty: 🔥 Priority (biggest gap) + ⚡ Quick Win (SRS due) + 🎯 Placement
Mission (days-to-assessment), each with its reason.

## 18. PLACEMENT SEASON MODE

45d: Learning > Practice > Projects → 30d: Learning + Assessment → 14d: Assessment +
Repair + Interview → 7d: Company Simulation + Weakness Repair → 48h: Revision + Recall +
Timed Simulation → Interview prep. Same graph, shifting priorities.

## 19. THE READINESS ENGINE

Readiness ≠ completion. Evidence dimensions: conceptual understanding, independent
solve, transfer, timed performance, consistency, recall stability, error recovery,
code quality, interview performance, recency. TARGET → CAPABILITIES → EVIDENCE →
GAPS → REPAIR → RETEST → UPDATED READINESS. Inspectable: why not ready, what blocks,
what to do today, highest-leverage fix.

## 20. READINESS MUST BE ACTIONABLE

Not "68%". But "68% — blockers: 1. Programming Logic 2. Timed Coding 3. SQL —
fixing #1 first = highest expected gain — [REPAIR THIS]".

## 21. CLOSED REPAIR LOOP

FAIL → DIAGNOSE → MISCONCEPTION → MICRO-LESSON → INTERACTIVE REPAIR → NEW CONTEXT →
RETEST → EVIDENCE UPDATE. Never Wrong → Retry.

## 22. PROGRESS THAT MEANS SOMETHING

Show movement (levels, concepts understood/repaired, projects, consistency,
readiness deltas) — but rewards represent capability, never empty clicks.

## 23. GAMIFICATION LAW

XP, levels, streaks, badges, quests, bosses, leagues, missions, rewards — with NO XP
FARMING, NO POINTS FOR EMPTY CLICKS, NO GUESS-SPAM REWARDS. Pay for: correct
prediction, transfer, independent proof, completed repair, consistent recall.
(Backed by repo Gamification Law: `record_practice()` sole writer, ledgered.)

## 24. AI TUTOR

Integrated into the lesson with modes TEACH/GUIDE/DIAGNOSE/DEBUG/REFACTOR/REFLECT,
receiving: concept, mission, stage, actions, attempts, mistakes, misconceptions,
mastery, target opportunity. Never a generic chatbot.

## 25. AI GUIDANCE HIERARCHY

LEVEL 0 re-read → 1 small hint → 2 leading question → 3 concept reminder →
4 partial approach → 5 worked guidance → 6 full explanation. Default: smallest
useful help. Make the learner capable, not dependent.

## 26. PROJECT LEARNING

learn → build → break → debug → extend → explain → showcase. Project evidence feeds:
implementation, problem solving, debugging, communication, software practices,
interview readiness.

## 27. SERVICE-BASED PLACEMENT PROJECTS

Beginner → intermediate → placement builds (Calculator … Library DB … Employee/Inventory
… REST API … Automation … SQL Analytics), progressing to API+SQL, auth, validation,
error handling, testing, logging, deployment. Transferable capability, not decoration.

## 28. CURRICULUM STRUCTURE

Capability graph: FOUNDATIONS (thinking, basics, decomposition, debugging) →
PROGRAMMING (variables…OOP…errors) → DSA (complexity…DP) → SQL (SELECT…optimization) →
APTITUDE (percentages…DI) → REASONING (relations…sufficiency) → CS FUNDAMENTALS
(OOP, DBMS, OS, Networks, SE) → PLACEMENT (timed coding, aptitude/reasoning tests,
debugging, simulations, mock OAs) → INTERVIEW (technical, DSA, CS, projects,
behavioral, HR).

## 29. FOUNDATION → SCREENING → INTERVIEW

One graph, three contexts. LOOPS: foundation = understand iteration; screening =
trace quickly; interview = explain complexity + edge cases.

## 30. COMPANY PREPARATION AS A LENS

Target company alters priority, frequency, difficulty, timing, distribution, mock
composition, repair priority, interview emphasis — never duplicates curriculum,
mastery, lesson engine, learner state, or question infrastructure.

## 31. TARGET SWITCHING

Change Company A → B without restarting. Recalculate fit, priorities, mocks,
interview focus. Mastery is retained.

## 32. THE PERSONALIZATION FORMULA

NEXT ACTION = f(learner gap, opportunity importance, prerequisite importance,
deadline, recent failure, SRS due, available time, confidence, expected learning
value). Never "next lesson in a list".

## 33. MICRO-INTERLEAVING

Planner mixes domains across the week (Programming + Aptitude recall + SQL +
Reasoning + simulation + repair/recall). No week-long single-domain blocks.

## 34. MOBILE-FIRST

Same learner state on PHONE/TABLET/DESKTOP. Mobile: large touch targets, minimal
typing, fast loading, short sessions, clear progress, one dominant CTA, instant
feedback, compact editor, swipe/tap. Desktop: deeper tooling.

## 35. "WHAT DO I DO NOW?" MUST ALWAYS BE EASY TO ANSWER

Every primary surface must expose: the current goal, today's mission, why this
mission was chosen, the single next action, and what happens after it. No surface
may leave the learner asking "what do I do now?"

# PART B — JUDGE-BASED ENGINE (cost architecture, locked)

**Rule: CORE LEARNING = DETERMINISTIC. AI = OPTIONAL ENHANCEMENT.**

## B1. Judge responsibilities (no LLM in the critical path)

- Coding → hidden tests, output checking, syntax/runtime errors, static checks, time/memory limits
- SQL → execution, expected-result comparison, schema validation, edge cases
- Aptitude → exact answer, step validation where possible, timing, misconception classification
- Reasoning → exact answer, reasoning path/state, rule-based diagnosis
- Interactive lessons → state validation (PREDICT/CHANGE compare expected vs learner state), manipulation/sequence checks
- Debugging → expected fix, changed lines, before/after behavior
- Projects → unit/integration tests, rubric checks, required functionality
- Readiness → deterministic evidence aggregation, mastery rules, timed-performance rules, repair completion

Judge the 11-step grammar deterministically: PREDICT/CHANGE = state comparison;
BUILD = tests; BREAK = predefined bug; FIX = behavior verify; TRANSFER = predefined
problem; PROVE = authoritative hidden tests.

## B2. Architecture

```
CONTENT REGISTRY + JUDGE ENGINE (coding/SQL/aptitude/reasoning)
        ↓ EVIDENCE ENGINE ↓ MASTERY/SRS/REPAIR ↓ READINESS
AI LAYER (separate, optional): Explain · Hint · Debug → personalization only
```

Mental model: JUDGE = referee, ENGINE = rules, CURRICULUM = levels, AI = coach.
The platform must fully work with AI unavailable. Spend priority:
curriculum+judge > UX/mobile > sandbox execution > AI tutor > AI extras.

## B3. Constraints (already repo law, restated)

- Prebuilt content through the trust pipeline; **no LLM authors/tags/grades bank content** (No-LLM Bank).
- Question content lives in versioned files, never MongoDB (Residency Rule).
- **Never execute student code via Python `exec()` inside FastAPI** — isolated execution only (Piston/sandbox path).
- AI never decides correctness where a deterministic judge can.
